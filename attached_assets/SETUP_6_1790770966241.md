## 2. Refund reconciliation — the correctness gap

```
artifacts/api-server/src/lib/refundReconciliation.ts
```

Nothing called `reverseCreatorCommission` or `clawbackPaidCommission`. A
refunded purchase left its commission standing, so you would have paid out on
money you had already given back.

One entry point, `reconcileRefund({ kind, refId })`, which:

- **Program A:** finds the grant, logs it, and **leaves the credits alone.**
  Bonus credits may already be spent; chasing them costs more in support than it
  recovers, and the 90-day expiry already bounds the exposure.
- **Program B:** reverses if the money hasn't left, claws back against the
  reserve if it has, and returns `needs_manual_review` when a batch is
  mid-flight — because `clawbackPaidCommission` correctly refuses to guess
  whether a transfer cleared.

**Wire it into both refund paths:**

```ts
import { reconcileRefund } from "../lib/refundReconciliation";

// routes/razorpayWebhook.ts — on refund.created / refund.processed
// routes/cashfreeWebhook.ts — on REFUND_STATUS_WEBHOOK (SUCCESS)
await reconcileRefund({
  kind: "credit_pack",        // or wallet_topup — match the original invoice kind
  refId: originalOrderId,     // the ORIGINAL payment's order/subscription ref
  refundedPaise: refundAmount,
  reason: "Refund processed",
});
```

The `refId` must be the **original payment's** reference, not the refund's —
that is the key both ledgers are indexed on.

Never throws. A refund has already happened; failing here would only trigger
gateway redelivery loops.

## 3. Payment instrument capture — the fraud signal

```
lib/db/src/schema/tenantPaymentInstruments.ts
artifacts/api-server/src/lib/paymentInstruments.ts
```

`bankMatchesOwnReferrals()` in `creatorPayouts.ts` was wired to ask whether a
payout destination matches an instrument used by one of the promoter's own
referrals. It had nothing to ask. This gives it the data.

**Capture** — call from both webhooks on every verified successful payment, at
the same point `recordInvoice` is called:

```ts
import { capturePaymentInstrument } from "../lib/paymentInstruments";

await capturePaymentInstrument({
  tenantId,
  gateway: "razorpay",
  method: payment.method,
  vpa: payment.vpa ?? payment.upi?.vpa ?? null,
  cardFingerprint: payment.card?.id ?? null,
  cardLast4: payment.card?.last4 ?? null,
  cardNetwork: payment.card?.network ?? null,
  issuer: payment.card?.issuer ?? payment.bank ?? null,
});
```

**Compare** — replace the stub body in `creatorPayouts.ts`:

```ts
import { payoutMatchesOwnReferrals } from "./paymentInstruments";

const match = await payoutMatchesOwnReferrals(input.creatorId, bankAccountHash);
if (match.matched) {
  // flag on creator_accounts.riskFlags — do NOT block
}
```

Hashing uses `hashPii` from `creatorPayouts.ts`, so both sides share the pepper
and scheme and are directly comparable. Only hashes and a last-4 persist.

**It flags, it does not block.** A shared family account is a real thing. But it
belongs in front of a human before money moves.

Migration: `pnpm --filter @workspace/db run push`, and export the new schema
file from `lib/db/src/schema/index.ts`.

## Two things worth knowing about what you already merged

**The payout runner got better than I wrote it.** Worth keeping: the advisory
lock giving one ordering for every financial mutation; the whole run in a single
transaction instead of my per-creator try/catch that swallowed partial failures;

and pay is caught; CSV formula-injection defence; reserve computed on the
payable base so a released reserve is never re-reserved; and `clawbackPaidCommission`
refusing `in_payout` rather than guessing.

payouts require manual review with no transfer date, replacing my "payouts run
monthly once you're past ₹1,000". Mine implied a cadence the system cannot
honour while payouts are manual. Keep the new wording.
