# Program A — Referral rewards on credit purchase

Moves the referral payout from **signup redemption** to **credit purchase**,
sizes both sides as a **percentage of what was paid**, resolves the referrer's
rate **live against a slab ladder**, and expires bonus credits after **90 days**.

Ordinary (non-referral) promo codes are untouched — they still grant on
redemption exactly as today.

Branch: `feat/prompt-kit-script-variants`

## Why `recordInvoice` is the hook

`lib/invoices.ts` is already the single choke point every verified-paid path
funnels through — verify routes *and* webhook backstops both call it, it only
fires on a confirmed terminal PAID state, and it's idempotent on `(kind, refId)`.
That is exactly the contract a purchase-triggered referral needs, so no route or
webhook file is touched by this change.

The referral grant carries its **own** idempotency (unique index on
`(purchaseKind, purchaseRefId)`), so it stays correct even if invoice creation
itself fails — which is why it's called *before* the invoice work rather than
inside its success branch.

## Defaults shipped

No admin action needed to run; every value is overridable per plan.

| Setting | Default |
|---|---|
| Slab 1 (0+ referrals) | referrer 10%, buyer 10% |
| Slab 2 (5+) | referrer 12%, buyer 10% |
| Slab 3 (15+) | referrer 15%, buyer 10% |
| Trigger | every purchase within the attribution window |
| Attribution validity | 180 days |
| Bonus credit expiry | 90 days |
| Earning purchase kinds | `credit_pack`, `wallet_topup` — **plan renewals excluded** |

Percentages convert to credits using the persisted `creditPricePaise`
(₹45/credit unless you've changed it). That value is frozen onto every grant
row, so changing the price later never rewrites history.

## Behaviour notes worth knowing

- **First code wins.** A second referral code entered later does not steal an
  existing attribution (`onConflictDoNothing` on the tenant PK). The redemption
  row is still written, so the attempt stays auditable.
- **Self-referral** is refused twice — once by the existing `own_code` check at
  entry, once again at grant time.
- **Slabs are live for the referrer, per-purchase for the buyer.** The referrer
  crossing a rung improves their *next* payout; past grants keep their frozen
  rate.
- **Plan renewals don't pay.** Only credit packs and wallet top-ups earn. Change
  `EARNING_PURCHASE_KINDS` if you want subscriptions to count.
- **Refunds are not yet clawed back.** The grant rows carry everything needed to
  reverse (`gross_paise`, both milli amounts, the purchase ref) — the reversal
  worker is deliberately out of scope here and belongs with the creator-program
  payout work, where money actually leaves.

## Tests to add

Existing suites to extend: `lib/promoCodes.test.ts`, `lib/referrals.test.ts`.

1. Redeeming a referral code grants **zero** credits and writes one attribution row
2. Redeeming an ordinary promo code still grants immediately (regression)
3. Two concurrent `creditReferralForPurchase` calls for the same `(kind, refId)` produce exactly one grant and one pair of credit grants
4. A purchase with no attribution is a no-op
5. An expired attribution is a no-op
6. `first_purchase` mode pays once; `every_purchase` pays repeatedly
7. Slab crossing: 5th qualifying purchase pays at rung 1, the 6th at rung 2
8. `referralsEnabled` off (globally or per-plan) blocks both attach and grant
9. Buyer bonus and referrer reward both expire at `referralBonusExpiryDays`
