## ⚠️ Codegen must run first

Both files import generated hooks from `@workspace/api-client-react`, which do
not exist until the OpenAPI contract carries the promoter paths and orval has
run. **The order is: contract → codegen → these files.** They will not compile
before that.

Set these `operationId`s in `lib/api-spec/openapi.yaml` so orval generates the
hook names used here:

| Path | operationId | Generated hook |
|---|---|---|
| `GET /promoter/me` | `getPromoterMe` | `useGetPromoterMe`, `getGetPromoterMeQueryKey` |
| `POST /promoter/apply` | `applyAsPromoter` | `useApplyAsPromoter` |
| `GET /promoter/commissions` | `getPromoterCommissions` | `useGetPromoterCommissions`, `getGetPromoterCommissionsQueryKey` |
| `POST /credits/creator-code` | `attachCreatorCode` | `useAttachCreatorCode` |

Once the generated types land, replace the three `any` annotations
(`Dashboard({ data }: { data: any })`, the commission row `r: any`, and the
mutation results) with the generated response types.


Conventions followed from `components/gamification-card.tsx`: generated hooks
with explicit `queryKey`, shadcn primitives from `@/components/ui/*`,
`useToast` from `@/hooks/use-toast`, lucide icons, `data-testid` on anything a
test would reach for, and semantic Tailwind tokens (`text-muted-foreground`,
`border-border`, `bg-primary/[0.03]`) rather than raw colours — so it inherits
light and dark mode for free.

## Edit 2 — navigation

The nav item should appear for everyone, not just existing promoters — the page
*is* the recruitment surface. It hides itself when the feature is off, because
`GET /promoter/me` answers 403 and the page renders the closed state.

If you'd rather not show it to everyone, gate the nav item on the
`creatorProgram` feature flag via the existing `features` hook, and leave the
route mounted so a shared link still works.

## Six states, one endpoint

`GET /promoter/me` decides everything:

| Response | Renders |
|---|---|
| 404 `not_a_promoter` | Application form |
| 403 `feature_disabled` | "Programme is closed" |
| 200 `applied` | Under review |
| 200 `approved` | Dashboard |
| 200 `rejected` | Reason, no code |
| 200 `suspended` | Dashboard with a suspended badge; earnings stay visible |

Note `retry: false` on that query — without it, TanStack Query retries the 404
three times before the application form appears, which reads as a broken page.

Suspended promoters still see their earnings. Hiding money someone has already
earned is how you turn a policy enforcement into a support ticket.

## The one screen element that matters

The pending-earnings explainer. A bare "₹4,200 pending" reads as *you are being
messed about*. The same number with

> 3 in the 30-day refund window
> 2 waiting on activation — the workspace needs to use 25% of the credits it bought

reads as a system with rules. It's the same data either way; only one of them
keeps a promoter from emailing support or quietly giving up. That block is built
off `awaitingActivation` and `inHoldWindow`, which exist in the API purely to
make it possible.

Related: the commission list shows `"Under review"` for held rows and nothing
more. Never surface which risk signal tripped — that teaches evasion.

## Copy decisions worth keeping

- **"Bonus credits are added when you buy, not now."** Under the code field.
  Applying a code grants nothing immediately; without this line the silence
  reads as a bug and generates support load.
- **"Ready to pay"** rather than "Payable" for the headline stat. It answers the
  only question a promoter has when they open the page.
- **The practitioner checkbox explains itself on tick** — NMC guidance appears
  inline rather than in a document nobody opens.
