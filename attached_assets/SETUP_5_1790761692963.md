# Promoter payouts — the last piece

PAN and bank collection, payout batches, TDS, reserve release, and clawback for
money that has already gone out.

Branch: `feat/prompt-kit-script-variants` · Apply after Programs A and B, the
promoter API and the promoter UI.

---

## The design call: the first payouts are manual

**This does not wire a payout API.** It batches, withholds TDS and reserve,
produces a reviewable batch and a bank-ready CSV, and waits for a person to
mark it sent.

Automating the first payouts of a new program means discovering an arithmetic
mistake by wiring money to strangers. Export, eyeball, pay, mark paid. Do that
for a few cycles, then automate.

`dispatchPayout()` in `lib/creatorPayouts.ts` is the seam. When you want
RazorpayX or Cashfree Payouts, implement it there — batching, the ledger and
the reserve logic don't change.

---

## Before anything else: two blockers

**1. Set `CREATOR_PII_PEPPER`** — at least 32 characters, in the server
environment. PAN and account numbers are HMAC-ed with it and never stored raw.

It must be set *before the first payout identity is saved*, and **must never
change afterwards**. Rotating it orphans every existing hash, which silently
breaks PAN deduplication — the control that stops one person running several
promoter accounts. Put it in whatever holds your other secrets, not in the
repo, and treat it as unrotatable.

**2. Get the TDS treatment confirmed by your CA.** The default is 2% on
commission under section 194H. The rate is a settings column so it's changeable
without a deploy, but the *treatment* — whether a GST-registered promoter
invoices you instead, how the certificate is issued, what you file — is not a
thing to guess at. Ironically, some of your promoters will be CAs.

## How the money actually moves

```
commissions in `payable`
        │
   buildPayoutRun()            ← batches per promoter; sends nothing
        │                        skips: below minimum · no bank details
        │                               · negative balance
        ▼
   payout [draft]              commissions → in_payout
        │
   exportPayoutBatch()         ← CSV; marks the batch `exported`
        │
   (a human pays the bank file)
        │
   markPayoutPaid()            commissions → paid
        │
   releaseMatureReserves()     ← after reserveReleaseDays, reserve returns
                                 as a positive ledger adjustment
```

Gross → withhold reserve → withhold TDS on the remainder → net. All three are
frozen onto the payout row, so a later settings change never rewrites what
someone was paid.

`markPayoutFailed()` puts the commissions back to `payable` and clears their
payout id, so the next run picks them up.

## Clawback — the case Program B refused

`reverseCreatorCommission` deliberately refuses a commission that is already
`in_payout` or `paid`, because you cannot un-send a bank transfer. This bundle
adds the honest version:

`clawbackPaidCommission()` writes a **negative ledger adjustment**. It is
absorbed by the promoter's reserve first, and whatever is left carries as a
negative balance that the next payout settles against. The promoter is never
asked to send money back — it just comes off what they earn next, which is
both simpler to operate and the only version that works in practice.

Idempotent on `clawback:<commissionId>`, so a redelivered refund webhook can't
claw back twice.

**Nothing calls it yet.** Wire it into your refund and chargeback path alongside
`reverseCreatorCommission` — try the reverse first, fall back to the clawback
when it refuses.

## The bank cross-check is present but inert

`bankMatchesOwnReferrals()` is called at the moment payout details are saved,
and currently always returns false. It's the check I flagged as the strongest
anti-fraud signal available: the same account paying in and receiving out.

To switch it on you need the payment instrument, which only the gateway
webhooks see. Roughly:

1. Add `tenant_payment_instruments` — `tenantId`, `instrumentHash` (HMAC of the
   UPI VPA, or card fingerprint + last4), `kind`, `firstSeenAt`
2. In `routes/razorpayWebhook.ts` and `routes/cashfreeWebhook.ts`, hash
   `payment.vpa` / `payment.card` and upsert on every successful payment
3. Replace the stub body with a join: any instrument belonging to a tenant that
   redeemed this promoter's code whose hash equals the payout `bankAccountHash`

Note UPI VPA and bank account hash are different strings, so hash a normalized
account identifier consistently across both sides, or compare on the VPA's
bank-account component where the gateway supplies it.

When it fires it **flags rather than blocks** — a shared family account is a
real thing — but it lands in `creator_accounts.riskFlags` for a human.

Worth doing before the first payout run, not before launch. It only matters
when money can leave.

## PII handling

- **PAN and account numbers are never stored.** HMAC-SHA256 with the pepper; only the hash, the last 4 and the IFSC persist.
- **`panHash` is uniquely indexed** — one payout identity per PAN across all promoter accounts. That is the dedupe control.
- **The save route never logs `req.body`**, and its error log deliberately omits the error object, which can carry the input. Keep it that way.
- **The CSV export carries no PAN** — beneficiary name, last 4, IFSC and amounts only. Payout files end up in inboxes and download folders.
- **Changing bank details clears `verifiedAt`**, so a changed destination re-enters verification rather than inheriting trust.

## Tests to add

1. `saveCreatorPayoutIdentity` rejects a malformed PAN, account number and IFSC
2. The same PAN on a second promoter account → `pan_in_use`
3. Re-saving for the same promoter updates in place and clears `verifiedAt`
4. `buildPayoutRun` skips: below minimum, no details on file, negative balance
5. Two concurrent runs produce one batch — the second updates zero commissions
6. Gross/reserve/TDS/net arithmetic on a known figure, including rounding
7. `markPayoutFailed` returns commissions to `payable` with a null payout id
8. `releaseMatureReserves` is idempotent — a second run adds no second adjustment
9. `clawbackPaidCommission` on a `paid` row creates one negative adjustment; a second call is a no-op
10. A negative balance is netted off the next payout and consumed exactly once
11. No route response ever contains `panHash`, `bankAccountHash`, or a full account number

Test 6 and test 10 are the two that matter most — they're the arithmetic, and
arithmetic is what you'd otherwise discover by underpaying someone.
